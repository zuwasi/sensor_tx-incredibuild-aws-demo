 Summary
--------------------------------------------------------------------------------
  We asked IncrediBuild support whether GCC/MinGW builds could be accelerated
  using a Linux SCL Helper on AWS EC2. Support replied: "It is OK and gcc is
  supported." Relying on that, we invested ~6 hours and incurred AWS EC2
  charges building the full SCL stack.

  After the SCL Helper failed to register, a full root-cause investigation
  found THREE independent blockers, two of which are product-level issues
  that support should have flagged before advising us to proceed:

  1. GCC is NOT supported by SCL (contradicts support guidance)
  2. SCL container crashes on every startup (Wine GetIpAddrTable bug)
  3. No GCC interception profile ships with IncrediBuild

--------------------------------------------------------------------------------
 Problem 1 - GCC not supported by SCL (contradicts support guidance)
--------------------------------------------------------------------------------
  Support told us: "It is OK and gcc is supported."

  Official docs (Linux Helper (SCL) Installation, updated 2025-12-22) say:
    SCL accelerates the following tools ONLY:
      - Cl.exe
      - Cl-filter.exe
      - Clang.exe
      - ShaderCompileWorker.exe (Unreal Engine)
      - Clang++.exe (Nintendo compiler)
      - Clang-Orbis.exe (PS4 compiler)
      - Clang-Prospero.exe (PS5 compiler)

  GCC (gcc.exe / g++.exe) is NOT in this list. Even with a perfectly
  registered helper, zero GCC compile tasks would be distributed to SCL.

  Request:
    1. Confirm in writing whether GCC/MinGW via SCL is supported or not.
    2. If yes, provide the interception profile entry and update the docs.
    3. If no, ensure support staff are aware so other customers are not
       misadvised.

 Problem 2 - SCL container crashes: GetIpAddrTable returns ERROR_FILE_NOT_FOUND
--------------------------------------------------------------------------------
  BuildService.exe crashes on every startup, so the Helper never registers.

  Helper BuildService.log (inside container Wine prefix):
    /root/.wine/drive_c/Program Files (x86)/Incredibuild/Logs/BuildService.log

    ----------Exception-----20-07-2026 12:51:05.539----------------
    EWin32Error Code=0x0EEDFADE PID=660 TID=684 Build=18415
    Failed to query size of IP address table: File not found (2)
    ----------Raised Exception--20-07-2026 12:51:05.540----------------
    Failed to load network configuration
    Failed to query size of IP address table: File not found (2)

  Reproduced on a FRESH container (destroyed and recreated) - not state
  corruption.

  Coordinator CoordinatorCore.log (Windows):
    20-07-2026 15:42:22.027 Agent ib-scl-helper turned online
    20-07-2026 15:42:37.853 Agent ib-scl-helper turned offline
    20-07-2026 15:43:34.574 Deleting offline agent ib-scl-helper
    (flickers online ~15 seconds, then crashes - repeats on every restart)

  Setup.exe hangs at "Verifying access permissions" for 3+ hours waiting
  for the already-crashed BuildService.exe.

  Root cause:
    IncrediBuild Delphi BuildService.exe calls the DEPRECATED Win32
    GetIpAddrTable API. Under Wine 8.0.2 in the SCL image, this API
    returns ERROR_FILE_NOT_FOUND (2).

  We verified Wine IP Helper stack is otherwise functional:
    $ sudo docker exec IncredibuildHelper bash -c 'WINEDEBUG=+iphlpapi wine ipconfig /all'
    0494:trace:iphlpapi:GetNetworkParams ... (works)
    0494:trace:iphlpapi:GetAdaptersAddresses ... (works)
    Hostname: ib-scl-helper, DNS suffix: tail84436b.ts.net

  GetNetworkParams, GetAdaptersAddresses, GetIpStatisticsEx all work.
  ONLY GetIpAddrTable fails. /proc/net/fib_trie, /proc/net/route, and
  /proc/net/if_inet6 are all readable from inside the container.
  --network host is in effect. This is a Wine API implementation gap,
  not a network or procfs visibility problem.

  Request:
    1. Patch BuildService.exe to use GetAdaptersAddresses instead of
       deprecated GetIpAddrTable, OR provide a Wine build where
       GetIpAddrTable is implemented against /proc/net.
    2. Provide a timeframe for a fixed scl:latest_10.36.x image.
    3. Provide a workaround if one exists (registry override, Wine config,
       env var, etc.).

--------------------------------------------------------------------------------
 Problem 3 - No GCC interception profile ships with IncrediBuild
--------------------------------------------------------------------------------
  Default BuildCache_profile.xml at:
    C:\Program Files (x86)\IncrediBuild\resources\BuildCache_profile.xml

  Defines interception entries for: cl, cl-filter, cld, link, lib, lld-link,
  clang-cl, clang++, clang-tidy, prospero-clang, orbis-clang, midl, csc,
  ccrh850, ecom800.

  NO <Tool Filename="gcc" .../> or <Tool Filename="g++" .../> entry exists.
  Only GCC-related reference in the entire profile set is a single line in
  chromium.ib_profile.xml for x86_64-w64-mingw32-as (the assembler).

  Even on a purely local IncrediBuild grid (no SCL, no cloud), wrapping a
  MinGW make invocation with IBConsole.exe /COMMAND="make ..." would NOT
  distribute any GCC compile tasks. This is consistent with what we
  observed: Build Monitor showed only the local machine (Ai-logic-lab,
  12 cores) and no helpers, even with /USECLOUDHELPERS=True.

  Request:
    1. Provide an official GCC/G++ interception profile (XML) for MinGW-w64
       toolchains, or confirm GCC interception is customer-supported-only.
    2. If custom profiles are the path, point us to documentation for
       writing a <Tool> entry for GCC (MinGW arg parsing, response files).
